# 1688 加購物車：要一個一個加，還是可以一次加很多？（評估）

> 2026-10-31（台北時間）。**只看程式碼和 repo 裡的文件，沒有做任何實際測試**，沒有連 Chrome、沒有打 1688、沒有動購物車。
> 每段都標了來源：**【程式碼／文件證據】**＝repo 裡看得到的事實；**【一般判斷】**＝依經驗推估，還沒在 1688 上驗證過。

## 結論（先講答案）

1. **現在的程式只能一次加一個規格**，而且是故意擋的：`mtop_mutate add` 每次只送 1 個規格，送多個會直接報錯。所以「一次把 29 個型號丟進去」目前做不到，也不建議硬改。【程式碼證據】
2. **需要間隔，但不用很久。** 建議每加一個規格停 **3～6 秒（每次隨機）**，每加 **8～10 個**再多停 **30～60 秒**。一輪（一批）最多 **30 個規格**，跑完一定要重讀購物車對帳。【一般判斷】
3. **同一個 1688 商品的多個規格「合併成一次送出」，等以後有真實紀錄證明可以再做。** 送出的資料格式本身是「清單」，技術上可能接受多筆；但 repo 裡只有「一筆」的真實成功紀錄，而且整頁補貨那條路以前就已經從「同商品一次送出」改成「逐筆送出」，因為一次送出時對不出是哪一筆失敗。【程式碼證據＋一般判斷】
4. **一出現滑塊／驗證碼／風控就整批停，不重試、不換路。** 登入掉了也是停。這部分程式已經有分類，只差批次層要「看到就停」。【程式碼證據】
5. **每一批加車前、加車後都要完整讀一次購物車，用前後差額確認每一筆有沒有真的加進去**（庭安的固定規則）。差額不對的那筆標「沒確認」，**不自動重送**，避免重複加。【程式碼證據＋庭安規則】

## 名詞（只解釋一次）

- **mtop**：1688 網頁背後用的 API 通道（網址是 `h5api.m.1688.com`），每次呼叫要帶簽章（sign）。
- **addcargo**：1688「加采购车」那支 API 的名字。
- **specId／skuId**：1688 商品的「規格編號」。加車 API 要的是 specId；Golden 表裡存的多半是 skuId，要先從商品頁換算。
- **goodsParams**：addcargo 送出的商品清單欄位，內容是「把清單轉成文字」的 JSON。
- **風控（risk control）**：1688 判斷「像機器人」時的防護，常見是**滑塊驗證**、`punish` 頁、`x5sec` 驗證 cookie、`RGV587`、`FAIL_SYS_USER_VALIDATE` 這類回應。
- **冪等（idempotency）**：同一個動作做兩次，結果跟做一次一樣。**加購物車不是冪等的**：同一筆送兩次，數量會變兩倍。
- **對帳（reconciliation）**：加車前後各讀一次購物車，比數量差額，確認真的有加進去。

## 1. 一定要一個一個加嗎？

**【程式碼證據】**

- `reverse_audit/mtop_addcargo.py`：
  - `stringify_goods_params()`：`goodsParams` 不是剛好 1 筆就丟錯「no batch spam adds」。
  - `build_addcargo_data()`：再檢查一次解碼後一定是 1 筆。
- `reverse_audit/mtop_http.py`：自己組的 addcargo 內容裡，只要出現 `batchAdd`、`goodsParamsList` 這類字就拒絕；API 名稱含 `batchadd` 也拒絕。
- `reverse_audit/mtop_restock.py` 的 `add_items()`：多個型號時是**一個一個呼叫 addcargo**（迴圈），整批前後各讀一次購物車對帳；差額不對就標 `clicked_unverified`，**不重送、不改用網頁點擊**。
- `alibaba_restocker.py` 的 `should_submit_offer_items_individually()`：註解寫「同 offer 多 SKU 真加車時改逐筆；單 SKU／dry-run 維持整頁一次送出」。也就是網頁點擊那條路**以前就從「同商品一次送出」改成逐筆送出**（相關修正：PR #21「harden per-SKU cart submit accounting」），原因是一次送出時，1688 的「加購成功」提示沒辦法對到每一筆，只能靠購物車差額確認。

**結論：** 以目前的程式，**是**一個一個加。這是安全設計，不是缺功能。

## 2. 可以一次加多個型號嗎？（API 本身接不接受）

**【程式碼／文件證據】**

- `docs/1688_cart_network_recon.md` 錄到的真實加車請求：`goodsParams` 是**轉成文字的陣列** `[{specId, offerId, quantity, flow, ext, selectedTradeServices}]`。每一筆都自己帶 `offerId`。
- repo 裡**只有 1 筆的真實紀錄**：`docs/1688_mtop_mutate.md` 記的第一次實測是加 1 筆成功（購物車 23→24 列）。**沒有任何「一次送 2 筆以上」的真實紀錄。**

**【一般判斷】**

- 欄位是陣列、每筆自帶 `offerId`，代表 1688 網頁本身在「同一個商品頁選好幾個規格、按一次加采购车」時，很可能就是送一個多筆的陣列。所以「**同一個商品的多個規格，一次送出**」大概率可行。
- 「**不同商品混在同一次**」：網頁上不會發生（加車是在單一商品頁按的），就算 API 收了，也比較像機器人行為，**不建議**。
- 就算 API 收多筆，也可能出現「回應說成功，但只有部分規格進車」的情況；目前回應格式我們只看過 1 筆的版本，不知道多筆時會不會逐筆回報。

**要改成「同商品一次送多筆」前，至少要先做到：**

1. 庭安同意後，拿 1 個商品、2 個規格、各 1 件，實測一次，存下脫敏後的回應（不存 cookie／token／sign）。
2. 前後購物車對帳證明 2 筆都進去。
3. 再放寬 `stringify_goods_params()` 的限制，而且只放寬到「同一個 offerId」，並設上限（例如一次最多 5 個規格）。

## 3. 一次全部丟進去的風險

| 風險 | 說明 | 依據 |
|---|---|---|
| 被當成機器人（風控／限流） | 短時間連續打 addcargo，容易觸發滑塊、`punish` 頁、`x5sec`。repo 已記錄：沒登入的 HTTP 讀商品頁幾乎都是 `punish`；之前 AI-4 的站內搜尋 253 筆裡有 97 筆卡驗證碼。 | 【文件證據】`docs/golden_ai_automation_review.md`、`docs/1688_mtop_mutate.md`；加車頻率上限多少會觸發是【一般判斷】 |
| 滑塊後硬重試 | 風控後還繼續打，通常會升級（更難的驗證、帳號暫時限制）。程式已把這類回應分類成 `risk_control`，提示寫「停，不要重試洗車」。 | 【程式碼證據】`mtop_http.classify_mutate_ret()`、`mutate_block_message()` |
| 登入中途掉了 | `_m_h5_tk` 過期或 session 失效時會回 `FAIL_SYS_SESSION_EXPIRED`／`TOKEN_EXPIRED`，後面全部失敗。 | 【程式碼證據】`mtop_read_cart.py` 錯誤分類 |
| 一部分成功、一部分失敗 | 批次中間斷掉時，前面已經加進去的不會自動退。若整批重跑，**已加的會再加一次**（加車不是冪等）。 | 【程式碼證據】`add_items()` 選擇「不重送」；冪等性是【一般判斷】 |
| 伺服器把數量併到既有列 | 同規格已在車內時，1688 可能直接把數量加到原本那列，而不是新增一列；所以只看「列數」會誤判，要看**該規格的數量差額**。 | 【文件證據】`docs/1688_cart_network_recon.md`（「伺服器可能併入既有 cartId」） |
| 購物車上限 | 1688 採購車有商品數上限，滿了會出現「采购车已满／已达上限」。整頁補貨那條路已經會偵測這些字、停下來並回報「已確認加入 X / Y 個」。mtop 這條路回應的錯誤字樣還沒看過。上限確切是多少，repo 裡沒有記錄。 | 【程式碼證據】`alibaba_restocker.CART_LIMIT_PHRASES`、`cart_full`；上限數字未知 |
| 用錯瀏覽器／帳號 | 第一批第 3 次就是因為程式可能另開一個 Chrome（不同登入狀態），所以停下。批次跑之前要確認 session 只來自指定的 CDP 埠。 | 【handoff 紀錄】`restock_batch1_20261030/batch1_add_result.md` |

## 4. 具體建議

以下數字是**【一般判斷】**，第一次跑時可以再保守一點，之後看紀錄調整。

### 4.1 分組

- **一筆 addcargo = 一個規格**（維持現狀）。
- 同一個 1688 商品（同一個 offerId）的規格**排在一起連續送**，中間用較短的間隔；換商品時用較長間隔。這樣比較像人在同一個商品頁慢慢加。
- 「同商品合併成一次送出」等第 2 節的實測做完、庭安同意後再開。

### 4.2 批次大小與間隔

| 項目 | 建議值 |
|---|---|
| 一批最多 | **30 個規格**（第一批 29 個剛好一批） |
| 同商品規格之間 | **3～5 秒**，每次隨機（jitter，也就是在範圍內隨機抖動，不要固定秒數） |
| 換商品之間 | **5～8 秒**，隨機 |
| 每 8～10 個規格 | 多停 **30～60 秒**，隨機 |
| 兩批之間 | 至少 **10 分鐘**，而且上一批對帳完成才開始 |
| 一天 | 不超過 **3 批**；有任何一次風控，當天就不再跑 |

以 29 個規格估算：大約 3～5 分鐘可以跑完，速度不是瓶頸。

### 4.3 退避（backoff）與停止規則

- **立刻整批停、不重試**（並回報「卡在哪」）：
  - 回應被分類成 `risk_control`（滑塊、`punish`、`x5sec`、`RGV587`、`FAIL_SYS_USER_VALIDATE`、驗證碼）
  - 回應是 `not_logged_in`（session 過期、token 失效）或 `bad_sign`
  - 出現「采购车已满／已达上限」
  - 連續 **2 筆**不明錯誤
- **可以等一下再試一次（只限沒有送出成功的那筆）**：網路逾時、連不上 —— 但**前提是**先重讀購物車，確認那筆**確實沒進去**，才能重送；讀不到購物車就當沒確認，不重送。
- **退避方式**：第一次等 30 秒、第二次 2 分鐘，再失敗就停。
- **絕不**：風控後換另一個瀏覽器、改用網頁點擊、清 cookie 重試、或自己去過滑塊。

### 4.4 加車前後對帳（庭安的固定規則）

1. **加車前**：用唯讀讀車（`python -m reverse_audit.mtop_read_cart`，同一個 CDP 埠）讀**完整**購物車，存檔。讀不到、讀不完整、遇到登入／驗證就**不開始**。
2. **逐筆加車**：每筆記下 offerId、specId、skuId（若有）、數量、回應分類、時間。
3. **加車後**：再完整讀一次購物車，對每個規格算「加車後數量 − 加車前數量」。
   - 差額 = 本次數量 → 成功
   - 差額 < 本次數量 → 標「沒確認」，**不自動補送**，交給人看
   - 差額 > 本次數量 → 標「異常（可能重複加）」，交給人看，必要時用 set-qty 改回（要另外核准）
4. 報告附上前後兩份購物車檔案、每筆結果、總件數。

### 4.5 目前程式和建議的差距（要做的話另開 PR）

| 差距 | 現況 | 建議 |
|---|---|---|
| 每筆間隔 | `mtop_restock.add_items()` 迴圈裡沒有等待 | 加隨機間隔與每 N 筆長停 |
| 遇到風控停 | 單筆會記錯誤，但迴圈會繼續送下一筆 | 遇 `risk_control`／`not_logged_in`／`bad_sign`／購物車滿 立即中斷整批 |
| 對帳讀不到 | 加車前讀車失敗時當作「空購物車」繼續 | 加車前讀不到就不開始 |
| 一批上限 | 沒有 | 預設最多 30 個規格 |
| 名稱對規格 | 沒 skuId 的型號無法加 | 另一個 PR（`feat/mtop-add-resolve-spec-by-name`）用商品頁的規格清單做「完全相同才算」的名稱比對，對不到或對到多個都報錯 |
